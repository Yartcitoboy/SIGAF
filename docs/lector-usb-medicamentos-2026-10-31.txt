LECTOR USB HID — SIGAF — 31 de octubre de 2026

Arquitectura revisada antes de programar
La aplicación existente es SIGAF, no una instalación de SAP: Next.js 16.3.6, React 19, TypeScript y Supabase/PostgreSQL. Las pantallas están en src/app/(dashboard); los formularios en src/componentes/modales; los servicios y validaciones en src/lib. La recepción guarda mediante crearLoteConInventario y el RPC recibir_lote, con trazabilidad, idempotencia y validaciones de stock existentes. Productos usa guardarProducto y el endpoint compartido /api/datos. Se conserva esta arquitectura, el login y las reglas de roles/sucursal.
La tabla real producto ya contiene id_producto, codigo_barras (VARCHAR 50 UNIQUE), nombre, descripción, presentación, categoría, principio activo, registro ISP y vida útil. No se crearon tablas, columnas ni migraciones. Se reutilizaron el parser GS1, la validación GTIN y los formularios actuales.

Funcionamiento
Un lector en modo USB HID actúa como teclado. No se necesita WebUSB, cámara ni una API externa para leerlo. El navegador debe estar activo y el campo del lector debe tener el foco. El botón Activar escaneo enfoca y selecciona ese campo. También se puede escribir o pegar el código y pulsar Buscar código o Enter.
El Enter del campo se intercepta con preventDefault y stopPropagation: inicia la consulta y no envía el formulario. Los botones de lectura y limpieza son de tipo button. En la ficha del medicamento también se bloquea Enter en el campo del código para impedir un guardado accidental. No se instala un capturador global de teclas que interfiera con otros campos.
El controlador evita repetir la misma lectura pendiente y los Enter de eco durante 700 ms. Si se inicia otra lectura, aborta la petición anterior e invalida su respuesta. Limpiar o cerrar el lector cancela la consulta. El contenido se selecciona para que el siguiente escaneo lo sustituya. No se guardan productos en el controlador ni en almacenamiento local.

Dónde se integró
1. Productos: lector en la pantalla existente. Si encuentra el medicamento, Admin abre la ficha existente ya completada, usando su ID, y puede revisar/editar lo permitido antes de Guardar ficha. Otros roles abren el detalle de consulta cuando tienen acceso a Productos. Si no existe y el código es válido, solo Admin puede elegir Registrar medicamento manualmente; se abre el formulario actual con el código y los demás campos vacíos. No se crea nada al escanear.
2. Lotes → + Recepción de lote: lector dentro del formulario existente. Identifica el producto en el backend, muestra su nombre y presentación y, si el GS1 incluye esos datos, completa lote y vencimiento. Un GTIN simple no contiene lote ni fecha: se deben transcribir del envase. Al cambiar el código se limpian producto, lote, vencimiento, fabricación, cantidad y costo anteriores para evitar mezclar dos medicamentos. Durante la búsqueda se bloquea la parte manual; el lector puede recibir un código nuevo. Un resultado inexistente o inválido no conserva el producto anterior.
3. La selección manual de medicamento sigue disponible. Para recibir un producto que no existe, Admin debe crear primero su ficha desde Productos y luego volver a recepción. Bodeguero no obtiene permisos para crear fichas y Auxiliar no obtiene permisos de recepción.
4. Solo Guardar ficha o Confirmar recepción ejecutan escrituras. Un escaneo no produce altas, movimientos ni stock. Se mantienen las validaciones de presentación, fechas, cantidad, costo, bodega y vida útil.

Endpoint y validación
GET /api/medicamentos/codigo?codigo=VALOR_CODIFICADO
Se usa parámetro de consulta en lugar de segmento para admitir con seguridad separadores y contenido GS1. La respuesta contiene producto (fila real autorizada), lectura {codigo, lote?, vencimiento?} y advertencia opcional. No expone claves administrativas. Exige la sesión y cuenta activa verificadas por autorizar; conserva RLS. Respuestas sin caché: 200 encontrado, 400 código inválido, 401 sin sesión, 403 sin perfil autorizado, 404 inexistente, 409 códigos ambiguos y 503 fallo de consulta.
Se admiten GTIN de 8/12/13/14 dígitos y códigos internos simples de hasta 50 caracteres. Para GS1 se utiliza el intérprete existente de AI 01, 10 y 17, con sus validaciones. Se conservan ceros iniciales, se retira el sufijo CR/LF y se reconocen prefijos habituales del lector. No se abren enlaces QR ni se ejecuta su contenido; no cualquier texto o URL QR representa un código de medicamento admitido.
Al buscar se comprueban las formas equivalentes de GTIN con ceros iniciales. Si varias fichas coinciden se devuelve 409, sin escoger arbitrariamente. En las escrituras web los códigos numéricos nuevos se normalizan a 14 dígitos, se comprueban equivalencias excluyendo la propia ficha y se mantiene la restricción UNIQUE de PostgreSQL para conflictos concurrentes. Las importaciones directas ajenas al endpoint deben respetar la misma normalización: no se añadió un trigger nuevo a la base compartida.
Se detectaron códigos históricos cuyo dígito de control no es válido. Si ya identifican una ficha, se permite localizarla con advertencia y conservar el mismo código al editar otros datos. No se admiten códigos numéricos nuevos con control inválido. No se corrigen registros históricos con valores inventados.

Cómo probar con el dispositivo físico
1. Conecta el lector al USB. Configúralo como teclado HID, con idioma de teclado igual al de Windows y un único sufijo Enter/CR. Para QR o DataMatrix el dispositivo debe ser un lector 2D; el software no convierte un lector 1D en uno 2D.
2. Puedes comprobar en Bloc de notas que entrega los caracteres y termina la línea. Para GS1 variable debe conservar el separador de grupo o estar configurado en representación compatible con el parser existente. No fotografiar ni subir códigos a un servicio externo.
3. Abre http://localhost:3102/lotes con una cuenta autorizada. Pulsa + Recepción de lote y Activar escaneo. Apunta al código de un medicamento ya registrado. Comprueba nombre y presentación. Para un GTIN simple ingresa lote y vencimiento manualmente; para GS1 comprueba los valores del envase antes de aceptarlos.
4. Completa y revisa cantidad, costo y ubicación. Solo pulsa Confirmar recepción cuando quieras registrar realmente el ingreso. Para comprobar sin modificar datos, cierra el diálogo.
5. Escanea otro medicamento: comprueba que sustituye el anterior y no mezcla sus campos. Usa Limpiar escaneo para reiniciar. Un código desconocido debe dejar la selección vacía e impedir confirmar sin un medicamento.
6. En Productos, prueba un código existente: debe abrir su ficha, no un alta nueva. Un código desconocido válido ofrece a Admin preparar la ficha manual con el código. No pulses Guardar ficha durante una prueba de solo lectura.
7. Escribe un código a mano y utiliza Buscar código: debe comportarse igual que el lector.
La versión compilada de prueba queda en el puerto 3102. Para iniciarla en otra sesión, ejecutar npm run build -- --webpack y, al terminar, npm run start -- --hostname localhost --port 3102.

AMPLIACIÓN: AUTOCOMPLETADO EN PRODUCTOS
Al escanear un código vinculado se abre la ficha con nombre, principio activo, presentación, categoría, ISP y vida útil existentes; no se deducen esos datos del número. El formulario distingue ahora la información recuperada de SIGAF de los datos del QR. Si hay titular_isp se muestra como Titular del registro ISP, sin presentarlo erróneamente como laboratorio fabricante.
El lote y el vencimiento codificados en GS1 se muestran en un bloque separado, incluso cuando se prepara un alta de código desconocido. No se guardan en producto: pertenecen a la recepción de un lote concreto. Con un GTIN simple esos datos no están presentes y deben transcribirse del envase.
Si el código no está vinculado, solo se completa el identificador y la información que realmente contiene el QR. Nombre, fabricante y demás datos necesitan una ficha existente o una fuente verificable; no se inventan. Una vez registrada o vinculada la ficha, los siguientes escaneos recuperan sus datos. Si el medicamento ya existe sin código, editar esa ficha evita crear un duplicado.
